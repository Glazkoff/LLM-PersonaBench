## Shared experiment contract

The only admissible fitness is the same frozen optimization-panel forecast route for every arm. The candidate is canonical JSON with exactly `role_definition`, `trait_formulations`, `facet_formulations`, and `critic_formulations`; trait/facet keys and respondent-specific intensity insertion remain fixed. Parse/schema failure receives the preregistered worst score, with a recorded attempted mutation; it must never silently become the parent while being counted as a new valid child. Scorer objective and direction are recorded explicitly. The model making questionnaire forecasts, the mutator/reflection model, prompt template, temperature, retry policy, seeds, train/opt/select panels and final selector must be identical where the algorithms allow it.

Define one full-panel equivalent as `N_opt * N_target_items` **executed** respondent–item model forecasts. The proposed search cap is `B=80` equivalents, including seed, parent minibatches, child minibatches, full-panel checks, retries that actually execute forecasts, and any validator or refiner calls. Log raw executed forecasts, cache hits, failed attempts, full-panel equivalents, evaluator calls, mutator/reflection calls, tokens and wall/GPU time separately. A ledger entry with no forward pass is not expenditure. Selection/calibration/test panels are separate and must not be read by the search adapters. Before any native optimizer evaluates a batch, the external evaluator should atomically reserve the exact respondent–item cost and reject a call that would exceed the cap; an internal optimizer stop counter alone cannot enforce this invariant.

The current `Fitness.evaluate()` returns a full-panel `rps_cal_opt`, while `evaluate_subset()` refits calibration on a subset (`src/optim/fitness.py`). This creates a **nonadditivity trap** for GEPA: a sum of per-respondent scores obtained with a single frozen/cross-fitted calibration rule is not generally the same as rerunning `crossfit_rps_cal` on arbitrary minibatches. Freeze the scoring rule and folds before search, expose honest out-of-fold per-respondent proper losses to GEPA, and separately compute the common full-panel selection score for recorded candidates. Do not claim that GEPA optimized the exact jointly refitted subset objective unless this equality is proved. Preserve invalid/missing forecast handling consistently across arms.

## Native GEPA adapter

The stable direct route is [`gepa.optimize`](https://gepa-ai.github.io/gepa/api/core/optimize/) with `seed_candidate: dict[str,str]`, `trainset` of optimization-panel respondents, a custom [`GEPAAdapter`](https://gepa-ai.github.io/gepa/api/core/GEPAAdapter/), `reflection_lm`, `candidate_selection_strategy="pareto"`, an explicit `reflection_minibatch_size`, `use_merge` setting, `seed`, and `max_metric_calls`. The [official adapter guide](https://gepa-ai.github.io/gepa/guides/adapters/) requires `evaluate(batch, candidate, capture_traces) -> EvaluationBatch(outputs, scores, trajectories)` and `make_reflective_dataset(candidate, eval_batch, components_to_update)`. Each `scores[i]` is **higher is better**; GEPA sums minibatch scores for acceptance and averages full validation scores. Therefore use `-per_respondent_RPS` (or a documented bounded monotone transform), one score per respondent, with aligned outputs/traces. The reflective records should contain only opt-panel question, forecast/answer discrepancy and sanitized diagnostic feedback, not selection/test answers. See the [API scoring semantics](https://gepa-ai.github.io/gepa/api/core/GEPAAdapter/).

Represent the entire canonical genotype as one component string, e.g. `{"persona_json": canonical_json}`, and parse/validate after each proposal. That keeps schema consistency; using four independent text components risks broken cross-field JSON and changed trait/facet keys. Render the immutable respondent intensities and questionnaire prompt only inside the adapter's evaluator. The reflection LM should use the same fixed mutator endpoint/model as the other arms through the officially supported callable/LM interface; pin and smoke-test the callable shape before labeling a run native. The direct adapter is preferable to a generic scalar `optimize_anything` wrapper here because it exposes per-respondent batch scores and diagnostic trajectories.

`max_metric_calls=80` would be wrong: GEPA counts example-level evaluation calls, not full-panel equivalents. With `N_opt` respondents, `80*N_opt` is only an approximate internal ceiling and does not account for repeated evaluation, forecast granularity or overshoot. Keep the outer executed-forecast cap authoritative. GEPA v0.1.4's release notes explicitly say stop conditions are checked between iterations and parallel proposals can overshoot; choose default single-mutation sampling and still enforce the outer cap. Reconcile GEPA `total_metric_calls`/callback events with raw forecasts after the run. Disable GEPA's evaluation cache unless its hits are exposed and accounted for, and keep `valset` entirely within the optimization panel; a separate held-out `D_select` cannot be fed to a search-time `valset`. The API defaults `valset=None` to the trainset loader and documents cache namespaces ([source API](https://gepa-ai.github.io/gepa/api/core/optimize/)).

Native GEPA retains its own Pareto selection, reflective proposal and optional merge behavior. The current `src/optim/arms/reflective.py::GEPA` manually selects a Pareto pool, calls the project's `ops.REFLECT`, checks a subset, then fills leftover budget with best-candidate mutations and even charges a fractional remainder without inference. That is method-inspired, and the latter charge must not enter actual cost.

The native package has a substantial Python stack (`hydra-core`, `langgraph`/LangChain, LiteLLM, NumPy/Pandas/SciPy, etc.); the private v2.20.1 checkout also declares `scikit-learn`, CatBoost and tracking/plotting packages. For the evaluator bridge, keep GigaEvo in its own process/environment and make `problems/persona/validate.py::validate(parsed_json)` call a versioned, local evaluator service that accepts canonical JSON and returns `{fitness, is_valid, raw_rps, executed_forecasts, ...}`. It does **not** mean 80 successful full-panel evaluator calls. The same atomic evaluator-side forecast cap, plus a finite native mutant cap and walltime, is required. The package's [`programs/README.md`](/Users/glazkov/Development/gigaevo-core-internal/gigaevo/programs/README.md) says `Program.iteration` increments per successful mutation dispatch while lineage generation is ancestry depth; neither is an evaluation budget. For the **public** v1.11.1 checkout, the documented problem contract is a Python program and `validate.py` ([quick start](/Users/glazkov/Development/gigaevo-core/docs/QUICKSTART.md)); the inspected public tree had no `json_document` config/feature.
